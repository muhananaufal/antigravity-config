# Custom Protoc Plugin Generator di Go (protogen)

## Konsep Utama dan Internal

Ketika perusahaan beralih ke arsitektur Microservices dengan Protocol Buffers (gRPC), *tooling* sering menjadi hambatan besar. *Developer* membuang ratusan jam membuat kode repositori, *HTTP Mux routers*, atau logika registri logger yang berulang-ulang dari skema API yang ada.

Proses de-facto mengatasi ini adalah menggunakan Protoc Plugins (e.g., `protoc-gen-go`). Bagaimana cara ia bekerja di balik layar? Perangkat compiler `protoc` (di C++) **tidak** merender kode sumber spesifik bahasa secara mandiri. Sebaliknya, protoc bertindak seperti penganalisis leksikal/parser murni. Ia menelan file skema `.proto`, membuat representasi AST biner padat (*Descriptor*), dan melemparkan kumpulan AST tersebut melalui *Standard Input (Stdin)* ke plugin biner Go kustom kita (`protoc-gen-custom`). Plugin ini mengartikannya, membangun sintesis kode Go, lalu mengembalikannya berupa struct hasil generasi file kembali melalui *Stdout* untuk akhirnya ditulis ke disk lokal oleh `protoc` core.

Package `google.golang.org/protobuf/compiler/protogen` menyediakan API *Type-Safe* tingkat mutakhir milik Google untuk menguasai komunikasi rumit Stdin/Stdout ini (menghapus kerepotan manual serialisasi *CodeGeneratorRequest* murni).

## Diagram Arsitektur Interoperabilitas Protoc (ASCII)

```text
  [1] Skema Def      [2] Protoc Engine        [3] Plugin Go Kustom Anda (protoc-gen-xxx)
                     (Compiler C++ Core)          (Menggunakan framework protogen)
  user.proto  --->   $ protoc --xxx_out=.  
                         |                    [Stdin]   +---------------------------+
                         | (Serializes AST) ----|-----> |   protogen.Options.Run    |
                         |                      |       |   Mengekstrak Descriptors |
                         |                              |   Membangun AST (*.go)    |
                         v                              +---------------------------+
               +--------------------+           [Stdout]              |
               | Writes File Output | <-----------|----- (Mengembalikan Data Response)
               +--------------------+
                         |
                         v
                user_generated.pb.go (Hasil File Disimpan ke Disk Host)
```

## Kode Go Production-Ready

Contoh plugin mutakhir yang menelusuri skema *Services* (RPC) proto dan membangun file interface Go untuk kebutuhan logging telemetri tambahan (misalnya: `*LoggerInterceptor`), memanfaatkan resolusi paket otomatis milik `protogen`.

```go
package protocplugin

import (
	"strings"

	"google.golang.org/protobuf/compiler/protogen"
)

// ==========================================
// 1. GENERATOR ENTRYPOINT
// ==========================================

// RunPlugin adalah titik mula eksekusi yang dipanggil oleh main()
// via `protogen.Options{}.Run(RunPlugin)`.
func RunPlugin(gen *protogen.Plugin) error {
	// gen.Files mengandung seluruh hirarki file (termasuk pustaka google/protobuf bawaan)
	for _, f := range gen.Files {
		// PERTAHANAN KRITIS: Jangan generate ulang struktur library standard (Dependency external).
		// Kita hanya ingin merender proto yang diamanatkan langsung oleh flag CLI pengguna.
		if !f.Generate {
			continue
		}
		
		// Proses File Spesifik
		generateFile(gen, f)
	}
	
	// Tidak me-return error mengisyaratkan pipeline protoc sukses
	return nil
}

// ==========================================
// 2. RENDERING LOGIC
// ==========================================

func generateFile(gen *protogen.Plugin, file *protogen.File) {
	// Abaikan file enum/message-only jika tidak ada satupun Service RPC yang dideklarasikan.
	if len(file.Services) == 0 {
		return
	}

	// Namakan target output sesuai base proto tetapi berakhiran _logger.pb.go
	filename := file.GeneratedFilenamePrefix + "_logger.pb.go"
	
	// Inisiasi struct File Generator bawaan. Framework akan menyelaraskan 
	// ident/resolusi imports cerdas (*Type-Safe Import Path*)
	g := gen.NewGeneratedFile(filename, file.GoImportPath)

	// Injeksi Standard Header
	g.P("// Code generated by protoc-gen-custom-logger. DO NOT EDIT.")
	g.P("// source: ", file.Desc.Path())
	g.P()
	g.P("package ", file.GoPackageName)
	g.P()

	// 1. Definisikan referensi eksternal (Library Import yang ingin kita injeksi secara dinamis).
	// Protogen akan secara pintar menambahkan header "import context" tanpa redudansi.
	contextPkg := protogen.GoImportPath("context")
	logPkg := protogen.GoImportPath("log")

	// 2. Lintasi (Traverse) semua komponen Service di File proto tersebut
	for _, service := range file.Services {
		
		// Render struktur antarmuka: type <X>Logger interface { ... }
		interfaceName := service.GoName + "LoggerInterceptor"
		g.P("type ", interfaceName, " interface {")

		for _, method := range service.Methods {
			// Resolusi tipe ident (Misal merujuk ke request type proto seperti: `*pb.CreateUserReq`)
			// g.QualifiedGoIdent melacak relasi paket lintas file .proto
			inType := g.QualifiedGoIdent(method.Input.GoIdent)
			
			// e.g. LogCreateUser(ctx context.Context, req *pb.CreateUserReq)
			g.P("    Log", method.GoName, "(ctx ", contextPkg.Ident("Context"), ", req *", inType, ")")
		}
		
		g.P("}")
		g.P()

		// 3. (Opsional) Generate Concrete Implementation Helper untuk Boilerplate Default-nya
		structName := "Default" + service.GoName + "Logger"
		g.P("type ", structName, " struct{}")
		g.P()

		for _, method := range service.Methods {
			inType := g.QualifiedGoIdent(method.Input.GoIdent)
			
			g.P("func (l *", structName, ") Log", method.GoName, "(ctx ", contextPkg.Ident("Context"), ", req *", inType, ") {")
			// Logika Body menggunakan package "log"
			g.P("    ", logPkg.Ident("Printf"), `("RPC Triggered: `, method.GoName, `")`)
			g.P("}")
			g.P()
		}
	}
}
```

### Unit Test (Emulasi Lingkungan Stdin/Stdout Linter Protoc)

Karena pengujian plugin `protoc` standar membutuhkan kompilasi biner `protoc`, para senior mensimulasikan injeksi `pluginpb.CodeGeneratorRequest` ke fungsi entry point secara terprogram di Go memory.

```go
package protocplugin_test

import (
	"testing"
	"google.golang.org/protobuf/compiler/protogen"
	"google.golang.org/protobuf/types/pluginpb"
	"mycustom/pkg/protocplugin"
)

func TestProtocPluginExecution_DoesNotPanic(t *testing.T) {
	// Simulasi Mock: CodeGeneratorRequest dikirimkan oleh core Protoc melalui Stdin.
	// Struct ini normalnya diisi jutaan baris AST binary Descriptor proto.
	req := &pluginpb.CodeGeneratorRequest{
		// ... Data descriptor tree diletakkan di sini untuk pengujian presisi tinggi ...
	}

	opts := protogen.Options{}
	plugin, err := opts.New(req)
	if err != nil {
		t.Fatalf("Failed to initialize mock protoc plugin environment: %v", err)
	}

	// Tes Eksekusi: Pastikan logika traverse loop tree AST tidak panic saat tree struct kosong.
	err = protocplugin.RunPlugin(plugin)
	if err != nil {
		t.Errorf("Plugin execution forcefully failed: %v", err)
	}
}
```

## Anti-Patterns

### ❌ Anti-Pattern 1: Merakit String Import/Dependencies Secara Manual dan Mentah
Banyak pengembang kuno (*pre-protogen era*) men-generate file go dengan melakukan modifikasi string `import` di pucuk struktur file via `.Replace()` string memori kotor, atau `fmt.Sprintf("import \"%s\"", pkgPath)`.

```go
// ❌ BAD: Menuliskan list imports raw dan memanggil hardcode package "fmt"
g.P(`import "fmt"`)
g.P(`import "context"`)
g.P(`func (s) Do() { fmt.Println("X") }`) // "fmt" tak tersambung ke AST
```
**Why dangerous:** Protobuf secara bawaan men-generate tipe yang tumpang tindih. Jika service `User` berada di file proto yang sama atau merujuk silang (cross-referencing) objek entitas (seperti timestamp dari paket opsional WKT Protobuf lain), merangkai `import` kaku secara manual memicu risiko **Duplikat Package Import** atau *Undefined Type Variables* yang memecahkan kompilasi seluruh file turunan.
**Solusi (Benar):** Jauhi hardcoding string. **Selalu panggil** `protogen.GoImportPath("path/to/pkg").Ident("TypeName")`. Framework `protogen` kemudian akan mengumpulkan seluruh variabel Ident tersebut di *background*, merangkumnya, dan membuat blok `import (...)` yang tepat, rapi, dan ter-resolusi penuh alias-nya secara cerdas di akhir durasi fungsi generator.

### ❌ Anti-Pattern 2: Gagal Memeriksa Bendera `File.Generate`
Melompati pengecekan *boolean* vital ini menyebabkan malapetaka polusi penyimpanan repositori lokal.

```go
// ❌ BAD: Memproses *SEMUA* file proto yang di-supply pipeline internal C++
func generatePlugin(gen *protogen.Plugin) {
    for _, f := range gen.Files {
       generateFile(gen, f) // Bencana File Dump!
    }
}
```
**Why dangerous:** Saat mengeksekusi `protoc`, _engine C++_ mem-parsing bukan hanya `user.proto` proyek, tapi juga file standard transitif `google/protobuf/any.proto` dan `google/protobuf/empty.proto` di latar belakang (yang di-import). Jika `!f.Generate` diabaikan, plugin Go naif ini akan men-generate seribu baris file kode untuk modul bawaan google dan meletakkannya di folder eksekusi host, merusak seluruh struktur commit dan lisensi pihak ketiga.
**Solusi (Benar):** Eksekusi *filter guard block*: `if !f.Generate { continue }`. Batasi mutlak sintesis di node domain milik target host lokal pengguna.

## Edge Cases & Defensive Programming Konkrit

1. **Identifier Tipe Bersinggungan Langsung dengan Reserved Keywords Go:**
   Skema proto adalah agnostik bahasa. Tim Data Analyst mungkin saja menamakan pesan protobuf `message error { string msg = 1; }` atau `message type { int32 id = 1; }`. Ketika digenerate ke Go struct, hal tersebut akan berbunyi `type error struct{}` atau `type type struct{}`, menabrak *built-in global keyword scope* (Keywords tabrakan).
   *Defensive:* Framework `protogen` otomatis meng-escape hal ini (menjadikan `Error`, `Type_`), tetapi untuk struct logika *Custom Handler* milik generator tambahan Anda sendiri (misal `type errorLogger struct{}`), pastikan menambahkan suffix semantik spesifik unik domain yang memperluas string identifier (seperti `type ProtoErrorXxxLogger`). Jangan memisahkan pemanggilan mentah.

2. **Perbedaan Model Bidirectional / Server / Client Streaming:**
   Apabila skema RPC berbunyi `rpc StreamChat(stream Msg) returns (stream Msg);`, tipe referensi input param via `method.Input.GoIdent` pada interface tak lagi sekadar Pointer struct mentah `*pb.Msg`. gRPC mewajibkan eksekusi streaming berjalan memeluk custom *Stream Interface Channel* (`[NamService]_[NamaMethod]Server/Client`).
   *Defensive:* Signature Generator harus melacak kondisional `method.Desc.IsStreamingClient()` dan `method.Desc.IsStreamingServer()`. Jika mengindikasikan `true`, ubah drastis tipe signature cetakan `g.P(...)` untuk tidak mengambil raw pointer (`*inType`), melainkan memanggil abstraksi *Interface Streamer Wrapper* miliknya. Terabas saja tanpa pengecekan, file output tak akan terbaca (compilation mismatch) oleh gRPC middleware implementasinya.

3. **Ketidaklengkapan Opsi 'go_package' pada Protobuf mentah:**
   Seringkali pengguna lupa meletakkan baris `option go_package = "myapp/pb";` di file proto mereka. Plugin `protogen` Go memiliki syarat (requirement) bawaan absolut menolak berjalan tanpa anotasi import absolut tersebut dan akan melempar _panic crash_.
   *Defensive:* Jangan berharap banyak untuk kode error transparan dari plugin. Untuk menembus dinding pertahanan, tegakkan linter skema (`buf lint`) pra-kompilasi, atau jalankan plugin dengan parameter flag *Compiler Override* (`protoc --custom_opt=paths=source_relative`) jika memaksa pergerakan output statis tanpa paksaan anotasi paket.
